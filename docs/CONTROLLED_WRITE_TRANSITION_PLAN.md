# Controlled Write Transition Plan

## 1. Purpose

Описать условия перехода от read-only Mail Assistant к контролируемым операциям изменения mailbox.

Главный принцип: никаких автоматических изменений без подтверждения пользователя. Любое будущее действие проходит цепочку:

```text
Analysis
   ↓
Preview
   ↓
User Confirmation
   ↓
Execution
   ↓
Audit Log
```

Этот план не включает исполнение и не изменяет mailbox.

## 2. Current Stable State

Текущая система включает:

- MCP server;
- Codex integration;
- Microsoft Graph read access;
- Mail classification;
- Folder design;
- Dry-run engine;
- Confirmation layer.

Текущие permissions:

- `Mail.Read`;
- `MailboxSettings.Read`;
- `User.Read`.

Текущий режим: **READ ONLY**.

## 3. Existing Pipeline

```text
Email
  ↓
Classification
  ↓
Action Planner
  ↓
Dry Run
  ↓
Confirmation
```

Текущий confirmation layer умеет создать pending request и изменить его локальный статус на approved, rejected или expired. Confirmation approved — это только решение пользователя, сохранённое в памяти процесса. После этого execution ещё отсутствует: Graph write API не вызывается, а письмо и mailbox не меняются.

## 4. First Write Operation

Первая рассматриваемая write операция будущего этапа — переместить **одно выбранное письмо** в заранее существующую и проверенную папку.

Не разрешается в рамках первого write сценария:

- массовая сортировка;
- автоматические правила;
- создание большого количества папок;
- выполнение нескольких изменений по одному общему подтверждению.

Папка назначения должна быть проверена заранее. Её создание не входит в первое действие.

## 5. Permission Review

Для write операций требуется отдельный анализ и согласование permissions. Возможный permission для операций с сообщениями — `Mail.ReadWrite`; необходимость этого и других минимальных разрешений должна быть подтверждена по конкретным Graph API операциям.

До включения write режима необходимо:

- проверить минимально необходимые scopes;
- провести review безопасности;
- обновить документацию и план реализации.

Сейчас `Mail.ReadWrite` и любые другие permissions не добавляются.

## 6. Controlled Execution Rules

Будущий исполнитель должен соблюдать правила:

1. Выполнять действие только после подтверждения актуального preview.
2. Обрабатывать только явно выбранное письмо.
3. За один запуск выполнять только одну операцию.
4. Записывать действие в audit log.
5. Проверять результат чтением после выполнения.

Отсутствие подтверждения, изменение предложения, неоднозначное состояние письма или ошибка должны остановить выполнение.

## 7. First Test Scenario

Сценарий предназначен только для будущей реализации после permission review, тестов и checkpoint. До включения execution никакие шаги не выполняют write операций.

Input: одно тестовое письмо и заранее существующая тестовая папка.

Будущий flow:

1. Прочитать тестовое письмо.
2. Выполнить локальную классификацию.
3. Создать proposal для перемещения одного письма.
4. Показать preview с исходной и целевой папками.
5. Получить явное подтверждение пользователя для этого proposal.
6. Выполнить одно перемещение.
7. Повторно прочитать состояние и проверить новую папку.

Текущая система может остановиться только после подтверждения; шаги 6 и 7 требуют отдельного разрешения и реализации.

## 8. Audit Requirements

Для будущей выполненной операции журналировать:

- message ID;
- исходную папку;
- целевую папку;
- timestamp;
- факт и контекст подтверждения пользователя;
- результат операции и ошибку, если она возникла.

Audit запись должна позволять соотнести исполнение с конкретным preview и подтверждённым proposal. До появления исполнителя approval не должен записываться как успешное выполнение.

## 9. Rollback

До будущего выполнения сохранять исходную папку, message ID и планируемое действие. После перемещения журналировать результат и фактическое состояние.

Для отмены предусмотреть возможность вернуть письмо в исходную папку после проверки его текущего расположения. Откат не гарантирован: перед ним нужно убедиться, что письмо не было дополнительно перемещено пользователем или другим процессом. Ошибки восстановления должны быть отражены в audit log.

## 10. Next Development Step

После утверждения этого плана создать ветку:

`feature/mail-organization-write`

В ней спроектировать и реализовать `Controlled Execution Engine` только после:

- отдельного permission review и согласования;
- тестов для одного тестового письма;
- checkpoint перед первым write изменением.

До выполнения этих условий система остаётся в режиме **READ ONLY**; этот документ сам по себе не разрешает Graph write операции.
