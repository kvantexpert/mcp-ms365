# Controlled Mail Organization Implementation Plan

## 1. Purpose

Описать технический план перехода от анализа писем к контролируемой организации mailbox. Этот документ планирует будущую работу и не разрешает запуск write операций.

Главный принцип: никаких автоматических изменений mailbox. Каждое потенциальное изменение проходит последовательность:

```text
Analysis
   ↓
Preview
   ↓
User Confirmation
   ↓
Execution
   ↓
Audit Log
```

Если пользователь не подтвердил точный предпросмотр, выполнение не происходит.

## 2. Current System State

В проекте уже существуют:

- MCP server;
- интеграция Codex;
- Microsoft Graph read access;
- локальная классификация писем;
- проект структуры папок.

Текущий режим: **READ ONLY**. Существующая реализация классификации анализирует переданные данные и не меняет mailbox. В рамках этого плана код, MCP tools, OAuth, permissions и Graph scopes не меняются.

## 3. Implementation Phases

### Phase A — Dry Run Engine

Цель — показать предлагаемые действия без их выполнения и без изменения mailbox.

Пример:

```text
Input:
Invoice email

Classification:
Finance

Planned action:
Move to Finance/Invoices

Result:
No mailbox changes
```

Dry run должен показывать исходные данные и предлагаемую цель, отмечать неоднозначность и явно сообщать, что никаких изменений не было. Если цель нельзя однозначно разрешить, действие получает статус review-required и не продвигается к подтверждению.

### Phase B — Action Proposal

Планировщик формирует данные предложения для проверки. Пример концептуальной модели:

```json
{
  "action": "move-message",
  "sourceFolder": "Inbox",
  "targetFolder": "Finance/Invoices",
  "messageId": "...",
  "reason": "invoice detected"
}
```

Это только предложение, а не команда Graph. Оно должно содержать достаточную информацию, чтобы пользователь мог понять, какое письмо и куда предполагается переместить. Для реализации следует определить валидацию идентификатора письма, исходной папки и целевой папки, а также поведение при неполных или устаревших данных.

### Phase C — Confirmation Workflow

Перед возможным выполнением пользователю показываются:

- полный список действий;
- количество писем;
- исходная и целевая папки;
- причины и сигналы классификации;
- элементы, требующие ручной проверки;
- явное указание, что будет изменено.

Подтверждение должно относиться к неизменённому, конкретному плану. Если план или состояние письма изменились, требуется обновить preview и получить новое подтверждение. Отсутствие, неоднозначность или устаревание подтверждения означает отказ от выполнения.

### Phase D — Execution

Фактическое выполнение рассматривается только после:

- отдельного review необходимых permissions и явного согласования;
- отдельного checkpoint;
- тестов на ограниченном наборе;
- проверки dry-run, confirmation и audit log;
- подтверждения пользователя для актуального плана.

Потенциальные действия этого будущего этапа: создание папки, перемещение сообщения, создание правила. Их реализация и вызов не входят в текущую работу. До прохождения всех gate условий действует READ ONLY.

## 4. Proposed Architecture

```text
User
  ↓
Codex
  ↓ MCP
MCP server
  ↓
Mail Organization Engine
  ↓
Action Planner
  ↓
Confirmation Layer
  ↓ (only after approved gates and explicit confirmation)
Graph Write API
```

Read-only анализ и preview не должны обращаться к Graph Write API. Архитектура должна обеспечивать невозможность перехода от предложения к исполнению без пройденных проверок и подтверждения. Конкретный механизм изоляции и включения будущих write capabilities определяется отдельным implementation design.

## 5. Required Components

### Classification Adapter

Использует существующую логику из `src/lib/mail-classification.ts` для получения категории, причин и рекомендованной папки из доступных полей письма. Результат классификации — вход для предложения, но сам по себе не запускает действие.

### Folder Resolver

Преобразует классификацию и утверждённую структуру в возможное назначение, например `Finance/Invoices` или `Clients/ClientName`. Resolver проверяет однозначность и наличие утверждённого соответствия. Неизвестные имена, конфликтующие правила и недостаточная уверенность требуют ручной проверки; автоматическое создание отсутствующих папок не предполагается.

### Action Planner

Создаёт неизменяемый список предлагаемых действий с идентификаторами писем, исходными/целевыми папками и причинами. План должен быть пригоден для точного preview, подтверждения и последующего сопоставления с результатами выполнения.

### Confirmation Manager

В будущей реализации связывает подтверждение пользователя с конкретной версией плана. До отдельного проектирования хранения и срока действия подтверждений никакие предположения о постоянном хранении не делаются. Изменение плана требует нового подтверждения; неподтверждённый план не исполняется.

### Audit Logger

Для будущих выполненных операций записывает инициатора, время, вид действия, идентификатор письма или папки, исходное и целевое состояние, результат и сведения об ошибке. До write этапа журналирование можно проверять на тестовых сценариях, не выполняя операций над mailbox.

## 6. Future MCP Tools

Потенциальные инструменты для отдельных будущих решений:

- `create-mail-folder`;
- `move-mail-message`;
- `create-mail-rule`;
- `preview-mail-actions`;
- `confirm-mail-actions`.

Это проектные названия, а не утверждение, что инструменты уже реализованы или доступны. Они не добавляются этим планом. Любое включение потребует отдельной реализации и review безопасности.

## 7. Security Requirements

До перехода к write режиму необходимы:

- новый checkpoint перед изменениями;
- отдельная проверка и согласование permissions;
- ограниченный тестовый сценарий;
- журналирование предложений и результатов;
- preview с точным перечнем изменений;
- явное подтверждение пользователя;
- остановка при неоднозначных данных, конфликте или частичном отказе.

Dry run не должен отправлять запросы изменения в Graph. Ошибки выполнения не должны приводить к незаметным повторным действиям. Любая неопределённость оставляет действие невыполненным до ручной проверки.

## 8. Permission Review

Текущие permissions:

- `Mail.Read`;
- `MailboxSettings.Read`;
- `User.Read`.

Для будущего write режима отдельно оценить `Mail.ReadWrite` и другие минимальные permissions только в случае необходимости для выбранных Graph операций. Требования нужно установить по документации конкретных API, разделяя перемещение сообщений, создание папок и управление правилами.

В текущем этапе permissions не меняются, scopes не добавляются, OAuth не изменяется.

## 9. Testing Plan

До реального использования будущей реализации предусмотреть:

1. Dry-run тест, подтверждающий отсутствие изменений mailbox.
2. Ограниченный тест с одним тестовым письмом после отдельного разрешения write режима.
3. Проверку результата: фактическое местоположение и корректность записи аудита.
4. Проверку rollback или документированного восстановления исходного состояния.
5. Проверку audit log: инициатор, время, действие, объект и результат.

Дополнительно проверить отмену и отсутствие подтверждения, устаревший preview, неоднозначную цель и частичный сбой. До согласования permissions и тестовой процедуры все проверки должны оставаться без write операций.

## 10. Rollback Strategy

Перед потенциальным действием будущая система сохраняет:

- исходную папку;
- идентификатор сообщения;
- целевую папку;
- версию подтверждённого плана;
- историю действия и результат.

Для перемещения следует предусмотреть обратное действие в исходную папку, если исходное состояние всё ещё доступно и обратный перенос безопасен. Перед rollback нужно проверить текущее расположение и не перезаписывать последующие пользовательские изменения. Откат не считается гарантированным; ошибки и невозможность восстановления должны быть записаны в журнал и показаны пользователю. Для созданных папок и правил необходимы отдельные обратимые процедуры до их включения.

## 11. Implementation Order

Предлагаемый порядок подготовки и будущей реализации:

1. Dry-run engine.
2. Action planner.
3. Confirmation layer.
4. Audit logging.
5. Permission review.
6. Limited write execution после прохождения всех gate условий.

Первые четыре компонента следует проверить в режиме без изменения mailbox. Переход к пункту 6 — отдельное решение, требующее checkpoint, согласованных permissions, тестов и подтверждения пользователя.

## 12. Next Step

После утверждения этого плана создать отдельную ветку `feature/mail-organization` для будущей реализации и отдельный checkpoint перед первым write изменением. До такого решения и прохождения проверок сохраняется текущий **READ ONLY** режим.
