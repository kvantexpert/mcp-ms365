# Controlled Mail Organization Design

## 1. Purpose

Определить безопасный подход к будущей организации почты после завершения read-only анализа.

Главный принцип: mailbox не изменяется автоматически. Любое изменение требует явного подтверждения пользователя для конкретного набора действий.

## 2. Current Foundation

К текущей основе проекта относятся:

- работающий `mcp-ms365` MCP-сервер;
- интеграция Codex с MCP;
- проверенный доступ Microsoft Graph для чтения почты;
- локальная детерминированная классификация писем;
- спроектированная структура папок.

Текущий режим: **READ ONLY**. Фаза проектирования не добавляет возможностей изменения mailbox и не меняет OAuth или permissions.

## 3. Phase 1.3 Goal

Цель будущей Phase 1.3 — спроектировать и, после отдельных проверок и согласований, внедрить контролируемую организацию почты:

- создание согласованных папок;
- перемещение выбранных писем;
- подготовка правил для отдельного последующего рассмотрения.

Переход к выполнению возможен только после проверки безопасности, permissions, тестирования и создания отдельного checkpoint. Сам этот документ не разрешает такие действия.

## 4. Safety Model

### Dry Run Mode

Сначала система формирует предварительный план без изменения mailbox. Для каждого действия показываются письмо, текущая папка, предполагаемое действие, целевая папка и статус ожидания подтверждения.

Пример:

```text
Email:
Invoice September

Current folder:
Inbox

Planned action:
Move to Finance/Invoices

Status:
Waiting confirmation
```

Предпросмотр должен позволять проверить точные письма и папки. Неоднозначные классификации и отсутствующие папки должны быть явно отмечены; система не должна молча выбирать альтернативу.

### Confirmation Mode

До выполнения пользователь видит сводку и подтверждает конкретный план, например:

> Переместить 5 писем в Finance/Invoices?

Подтверждение относится только к показанному списку. Если состав или назначение изменились, требуется сформировать новый предпросмотр и запросить подтверждение снова. Без однозначного подтверждения выполнение не начинается.

### Execution Mode

Выполнение означает фактическое изменение mailbox. Оно может быть рассмотрено только после:

- отдельного checkpoint;
- проверки необходимых permissions и их согласования;
- тестирования на ограниченном безопасном наборе;
- утверждения плана и подтверждения пользователя.

До выполнения всех условий активным остаётся read-only режим.

## 5. Allowed Future Operations

Потенциальные будущие операции:

- создание папки через `create-mail-folder`;
- перемещение сообщения через `move-mail-message`;
- создание правила через `create-mail-rule`.

Они описаны как проектные требования. Сейчас инструменты не добавляются и операции не выполняются. Создание правил может иметь отдельные последствия и требует самостоятельного проектирования, проверки и подтверждения.

## 6. Required Permissions Review

Текущие permissions:

- `Mail.Read`;
- `MailboxSettings.Read`;
- `User.Read`.

Для будущих write-функций необходимо отдельно определить минимальные требуемые delegated permissions. `Mail.ReadWrite` может потребоваться для некоторых действий с сообщениями, но необходимость и дополнительные разрешения, особенно для управления папками или правилами, должны быть проверены по конкретным Graph API операциям.

На этом этапе permissions не добавляются, scopes не расширяются и согласие пользователя или администратора не запрашивается.

## 7. Rollback Strategy

До любой ограниченной серии изменений будущая система должна сформировать и сохранить для проверки:

- предпросмотр операций;
- точный список затрагиваемых сообщений и папок;
- подтверждение пользователя;
- журнал выполненных действий с идентификаторами объектов, исходными и целевыми папками, результатом и временем.

Для перемещений журнал должен содержать достаточно сведений, чтобы оценить возможность обратного переноса. Откат не считается гарантированным: доступность исходной папки, сохранность элементов и Graph permissions должны быть проверены. Создание правил и папок также требует отдельного плана отмены. Ошибка или частичное выполнение должны быть явно отражены, без повторения действий вслепую.

## 8. Testing Strategy

До применения к рабочим письмам будущую реализацию следует проверить:

- на отдельной тестовой папке и тестовых сообщениях;
- на небольшом, явно ограниченном наборе;
- сначала в dry-run режиме;
- с проверкой фактического результата и журнала;
- с проверкой отказа или остановки при отсутствии подтверждения.

Следует также проверить частичные ошибки, повторный запуск и поведение при конфликте целевой папки. Реальные изменения допустимы только после отдельного согласования тестового плана и разрешений.

## 9. Future MCP Tools

Потенциальные инструменты:

- `create-mail-folder`;
- `move-mail-message`;
- `create-mail-rule`.

Это не реализованные возможности. Их включение возможно только по отдельному решению после завершения проектирования, проверки безопасности и permissions.

## 10. Development Sequence

Предлагаемая последовательность:

1. Завершить и согласовать дизайн.
2. Провести отдельный review необходимых permissions.
3. Создать отдельную feature-ветку и зафиксировать исходный checkpoint.
4. Спроектировать и реализовать dry-run, пока без фактических изменений mailbox.
5. Спроектировать и проверить workflow подтверждения пользователя.
6. После отдельного решения и новых проверок ограниченно включить write operations.

Каждый переход требует проверяемых результатов, тестирования и документации. Успешный dry-run сам по себе не включает режим выполнения.

## 11. Next Step

После утверждения этого документа подготовить отдельный план реализации Phase 1.3 с границами работ, критериями проверки, требованиями к permissions и условиями остановки. До утверждения плана и отдельного checkpoint проект остаётся в режиме **READ ONLY**.
