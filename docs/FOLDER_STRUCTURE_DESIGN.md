# Folder Structure Design

## 1. Purpose

Создать понятную структуру хранения писем Microsoft 365 для будущей автоматизации.

Основные задачи:

- уменьшить хаос Inbox;
- группировать письма;
- облегчить поиск;
- подготовить основу для автоматической сортировки.

## 2. Current State

Сейчас система работает в режиме **READ ONLY**.

Доступные возможности:

- чтение писем;
- анализ писем;
- классификация.

Недоступно:

- создание папок;
- перемещение писем;
- изменение mailbox.

Этот документ описывает будущую структуру. Он не разрешает и не выполняет изменения mailbox.

## 3. Folder Architecture

Предлагаемая структура:

```text
Mailbox
├── Clients
│   ├── Client_A
│   └── Client_B
├── Projects
│   ├── Project_A
│   └── Project_B
├── Finance
│   ├── Invoices
│   ├── Payments
│   └── Contracts
├── Documents
├── Security
├── Automation
└── Archive
```

Имена `Client_A`, `Client_B`, `Project_A` и `Project_B` — примеры. Реальные папки и правила именования требуют отдельного согласования.

## 4. Folder Classification Rules

Результат классификации может быть использован как рекомендация папки. Примеры:

| Email                 | Classification | Suggested folder      |
| --------------------- | -------------- | --------------------- |
| Invoice from supplier | Finance        | Finance/Invoices      |
| Project meeting       | Projects       | Projects/Project_Name |
| Security alert        | Security       | Security              |

Рекомендация сама по себе не перемещает сообщение и не изменяет mailbox.

## 5. Relationship With Email Classification

```text
Phase 1.1: Email Classification
                 ↓
Phase 1.2: Folder Structure Design
                 ↓
Phase 1.3: Controlled Mail Organization
```

Phase 1.1 определяет аналитическую категорию и возможную папку. Phase 1.2 задаёт и документирует целевую структуру. Изменения mailbox рассматриваются отдельно в Phase 1.3.

## 6. Sender Based Organization

В будущем отправитель может помочь предложить клиентскую папку, например:

```text
client@example.com
        ↓
Clients/Client_Name
```

Связь адреса с организацией или папкой должна быть проверена. Один только домен или имя отправителя не является основанием автоматически перемещать сообщение.

## 7. Topic Based Organization

Базовые тематические категории:

- Clients
- Projects
- Finance
- Documents
- Security
- Automation
- Personal

Категория классификации может предлагать папку с тем же назначением. Вложенная папка предлагается только при наличии достаточно ясного сигнала, например типа финансового документа или известного проекта.

## 8. Rules Priority

Предлагаемый порядок выбора целевой папки:

1. явное совпадение с проектом;
2. известный отправитель;
3. финансовые ключевые слова;
4. ключевые слова безопасности;
5. общая категория.

Если несколько правил конфликтуют или сигнал недостаточно определён, результат следует пометить для проверки пользователем, а не выбирать действие автоматически.

## 9. Safety Model

Текущий режим: **READ ONLY**.

На этапе проектирования разрешены чтение, анализ и рекомендации. Создание папок, перемещение писем и любые другие изменения mailbox не выполняются.

Будущие write operations потребуют:

- отдельной ветки;
- отдельной проверки permissions;
- тестов;
- отдельного checkpoint.

## 10. Future MCP Requirements

Для возможного будущего этапа могут потребоваться инструменты:

- `create-mail-folder`;
- `move-mail-message`;
- `create-mail-rule`.

Эти инструменты только перечислены как потенциальные требования. Они не реализуются и не включаются в текущем этапе.

## 11. Next Steps

После утверждения структуры следующий этап — **Phase 1.3: Controlled Mail Organization**. Планируемые элементы этапа:

- создание согласованных папок;
- перенос тестовых писем;
- dry-run режим для предварительного просмотра предлагаемых изменений;
- подтверждение пользователя перед применением изменений.

Phase 1.3 требует отдельного плана, проверки безопасности, тестов, документации и checkpoint до выполнения любых изменений mailbox.
